# Hexis

App iOS **perso** de musculation + alimentation (1 utilisateur). **Deux apps, un seul code** : « Hexis » (la sienne) et « Hexis Elle » (une proche : cible `HexisElle`, drapeau `ELLE`, `Edition.hasNutrition`, programme dans `HexisElle/Program.json`, bundle `com.example.Hexis.Elle`, un iPhone = une base : pas de profils). SwiftUI + SwiftData, 100 % local. UI en **français** ; code, commentaires, commits en **anglais**.
Principe : minimaliste, **automatisée**, ultra guidée. Un bouton évident par écran ; l'app décide, **dit ce qu'elle fait** et ne demande rien à valider. Lecture/utilisation pure : aucune config, aucun import, aucune édition dans l'app (le programme se change dans `Resources/Program.json`).
Documentation par sujet : `docs/00-apercu.md` à `90-glossaire.md` (lire seulement ce que la tâche touche ; règles de calcul : `docs/20-regles.md`). Backlog : `ROADMAP.md`.

## Démarrer une conversation

Rapport `À CORRIGER` : le traiter en premier (cause, test, correctif). Ne pas ré-explorer le projet ; ouvrir seulement les fichiers de la tâche (grep + `offset/limit`). ## Contraintes dures (compte Apple gratuit, ⌘R chaque semaine)
- Local uniquement. Pas de CloudKit/push/App Groups/Watch/widgets d'écran d'accueil (seule exception : la Live Activity de repos, cible `HexisWidgets` + code partagé `HexisShared/`, sans App Group). **Pas de dépendance externe sans demander.**
- **Bundle ID `com.example.Hexis` : jamais le changer.** App jamais désinstallée. Projet dans `~/Developer/Hexis`, jamais dans Documents/Desktop (iCloud).
- Tout changement de `@Model` = nouvelle `VersionedSchema` (actuel **V16**) + étape du `SchemaMigrationPlan`. **Jamais modifier une propriété d'un `@Model` livré** (crash au lancement) : nouveau modèle lié par UUID. Tout nouveau modèle : `BackupDocument` + `BackupService`.
- Secrets (`Hexis/Secrets.plist`, ignoré par Git) : jamais dans Git, jamais affichés/commités.
- **Un seul `NavigationStack`**, dans `RootView`, autour du pager de 6 écrans (3 Muscu : Accueil, Programme, Historique ; 3 Alimentation) ; plus de Réglages. Jamais un `NavigationStack` ni un `.toolbar` par écran racine (crash UIKit au swipe) : boutons d'action en `PageActionRow`, rangée dans un `VStack` (pas de `safeAreaInset` autour du pager ni dans ses pages : suspect d'une boucle de mise en page qui a gelé l'app). La barre du bas (`RootTabBar`, Liquid Glass) flotte en `overlay` sur le pager (le verre déforme ce qui défile dessous) ; marge basse par `.contentMargins` sur le pager. Les écrans poussés recouvrent tout le pager. La séance en cours est présentée par `RootView` (`ActiveWorkoutView`), jamais depuis une page du pager. Seul geste : un glissé horizontal sur la rangée du haut (`ModeSwitcher`) bascule Muscu/Alimentation, depuis n'importe quel écran ; aucun autre geste global. Confirmations en `.alert` (jamais `.confirmationDialog` : popover mal placé dans le pager) ; pas de swipe action (le pager prend le geste).

## UX
Mode Jour/Nuit seulement (bouton soleil/lune dans la rangée du haut, `AppearanceToggle`, nuit par défaut, noir pur) : toute couleur via `Color(light:dark:)` dans `Theme`, `.appAppearance()` sur la racine et chaque sheet ; **une seule couleur d'accent** (+ une couleur par superset), SF Symbols, look Apple Music (cartes sans bordure aux gris Apple, boutons capsule en Liquid Glass, verre **neutre** : l'accent seulement sur le symbole/texte sélectionné, jamais en teinte de verre), haptics discrets, taps ≥ 56 pt. Tout style via `Theme/Theme.swift` (rien en dur dans les vues). Séance façon Hevy (liste d'exos avec leurs séries, exo actif en surbrillance, saisie en bas, repos en bandeau). Supersets = barre de couleur (une par superset, même couleur dans Programme et Séance), sans texte ni « 1a/1b ». Toutes les cartes restent ouvertes : saisie libre dans n'importe quel ordre (machine prise), l'ordre réel est enregistré. Accueil : salle, prochaine séance, « Commencer », carte « Ajusté pour toi ». Effort au **RPE** ; seuls « Fatigué »/« Gêne » en ressenti ; jamais le mot « dur ». Peu de texte, bons défauts, afficher peu et calculer beaucoup en arrière-plan.

## Architecture
Dossiers, flux d'une séance, données : `docs/30-architecture.md`. Muscu : `SessionAdjuster` décide, `SessionPlan` construit, `TrainingCycle`/`AutoDeload` le cycle, `Rehab` la réhab ; `Workout/` et `Nutrition/` ne se connaissent pas. Vues sans logique métier (logique pure dans `Services/`), `@Observable`, `@Query`, `#Preview` par vue, un type principal par fichier, pas de `!`/`print`, vues < ~150 lignes.
**Doc** : `docs/*.md` (source) → `python3 Tools/doc.py` → `docs/index.html` (généré). Changement de fonction/règle/outil ⇒ mettre à jour le fichier `docs/` concerné dans le même commit.

## Qualité (obligatoire, détail : `docs/50-qualite.md`)
- **`zsh Tools/check.sh`** = le seul contrôle : audit statique, tests de logique, simulateur de vie (athlète virtuel qui vit des mois avec le vrai `WorkoutViewModel`, la vraie base et le vrai `Program.json`), compilation iOS. **Deux passes** : « Hexis », puis « Hexis Elle » recompilée avec `ELLE` (son programme, ses vies `#if ELLE`, sa sauvegarde `her-latest.json`). Le hook Git refuse tout commit rouge. `deep` = 8 vies/scénario + vraies données de l'iPhone (`Tools/data_check.sh`).
- `check.sh` montre aussi **« ce que l'utilisateur verra »** : diff de l'Accueil, des séances préremplies, d'Aujourd'hui et des courses sur la dernière sauvegarde de l'iPhone. Tout changement listé doit être voulu et **dit dans la réponse** ; un changement non voulu = bug.
- Bug trouvé = d'abord un test qui échoue (`Tools/LogicTests` : unitaire, ou `Habits`/`LifeTests`/`LifeChecks` pour un comportement de vie), puis le correctif, puis se demander comment l'attraper seul la prochaine fois (règle `Tools/audit.py`, `LifeChecks`, contrôle `RealDataTests`). Toute règle de calcul nouvelle ou changée a son test.
- **`/chasse`** : chasse aux bugs par zone (cas concrets de la vie réelle), journal dans `docs/50-qualite.md`. En boucle : `/loop /chasse`.
- Crash ou gel : **d'abord `python3 Tools/crashlog.py`** (`0x8BADF00D` = thread principal bloqué > 10 s), ne pas deviner. L'utilisateur teste sur iPhone 15 Pro Max (⌘R), **toujours en Release** (Debug seulement s'il le demande) : le lui rappeler dès qu'il s'entraîne. Pas de simulateur ni de captures ; ne jamais écrire « pas testé / pas vu le rendu ».
- Pièges connus : jamais de `.task`/`.onAppear` sur un `Group` qui peut être vide (ne tourne jamais : `VStack`, contrôlé par l'audit) ; jamais de `Date.now`/valeur changeante dans un `@Query`/`#Predicate` construit dans un `init` de vue (boucle, gel) → chargement unique par `ModelContext` dans `.task` ; jamais de calcul sur tout l'historique dans `body` ; recherches par `Set`/`Dictionary`. Tout ce qui lit l'heure prend un `now:` (le simulateur voyage dans le temps).

## Workflow
- Pas de plan écrit : coder, choisir les détails soi-même. Réponses courtes. **Demander seulement** pour : dépendance externe, choix de données majeur/irréversible, action destructrice, info que seul l'utilisateur a. Une question, avec une recommandation.
- Enchaîner les tâches de `ROADMAP.md` ; **un commit par feature** (`feat:`/`fix:`/`chore:`, ligne Co-Authored-By du harnais) incluant `ROADMAP.md` ; après un changement d'architecture/modèle/règle : une ligne dans `CLAUDE.md`/`docs/`.
- Fin de feature : `check.sh` vert, relecture de ce qui a été touché (bug, perf, écran trop chargé), code mort supprimé, au plus 1-2 idées à forte valeur (automatiser plutôt qu'ajouter un écran). Fin de réponse : 2-3 lignes (fait + quoi tester sur l'iPhone).
- Avant de s'arrêter ou contexte rouge : mettre à jour « Prochaine action » dans `ROADMAP.md`.
- Contexte (status line) : jaune ≥ 50 % après une feature commitée ou changement de sujet → dire « bon moment pour relancer une conv neuve (Xk tokens) » ; rouge → toujours ; session/semaine ≥ 90 % → le signaler. Économiser : appels parallèles, `grep` avant `Read`, lectures partielles, sorties courtes, pas de sous-agent sans besoin.
